# `provider_nodes` schema design (Y3)

Status: design document, **no DDL in this file has been applied anywhere.**
Deliverable for `docs/yogitasks.md` Y3. The application half — choosing a
migration tool and actually running something against a database — is Y4 and
is explicitly blocked on this document plus a decision from R1.

## 0. What this document is actually documenting

Y3 is framed as a green-field design ("M0 has no tables at all and that is
deliberate ... this work exists so M1 starts from a considered design"). That
framing is no longer accurate and it would be dishonest to write this as if
it were. `provider_nodes` already exists, is live, and has evolved past M1:

- The table shipped in PR #38 (`docs/Tasks/tasks.md` M1 item 1, owned by R9),
  landed directly in `orchestrator/schema.sql`, with no design document
  preceding it.
- It was extended twice more by idempotent `ALTER TABLE` statements:
  `node_token_hash` (node credential, ships with the authenticated-heartbeat
  work), and `render_eligible` / `blender_version` (ADR 0006, the rendering
  vertical).
- It is currently running on the production database (Render), per ADR 0005's
  own account of the deployment history.

So this document is not "the design that will become the table." It is the
design record that should have existed before PR #38, written now, against
the table as it actually stands, so that:

1. the shape has a considered rationale on paper instead of only in
   scattered inline comments,
2. Y4 has something to migrate *from* a stated design rather than reading
   `schema.sql` cold, and
3. the places where the shipped shape is questionable, or where this task's
   own instructions no longer match reality, are named explicitly instead of
   quietly inherited.

**Sources consulted**, in order of authority for this table:

- `orchestrator/schema.sql` — the live DDL (`provider_nodes` at lines 18–59,
  plus the later `ALTER TABLE provider_nodes` statements at lines 180–181,
  354–363).
- `orchestrator/models.py` — the Pydantic wire contract (`Capability`,

- `orchestrator/liveness.py` and `orchestrator/tests/test_liveness.py` — the

- `orchestrator/main.py` — `register`, `heartbeat`, `list_nodes`, and

- `agent/identity.py` — how `node_id` is derived and persisted on the

- ADR 0004 (unauthenticated heartbeat) and ADR 0005 (provider accounts) —
  the two decision records that already touch this table.
- `packages/contracts/src/schemas.ts` — read per this task's own instruction.

## 1. DDL & column specification

This is the table as it should be described if it were designed as one
unit, folding in the columns that historically arrived by later `ALTER
TABLE`. It is not a proposal to change anything — every column below
already exists in `orchestrator/schema.sql` with this type and nullability.

```sql
CREATE TABLE provider_nodes (
    -- Identity. See §2. Chosen by the agent, not generated by the database.
    node_id             TEXT PRIMARY KEY,

    -- Capability: hardware facts, refreshed on every register (upsert).
    -- Changes rarely (a driver update, a new GPU) but is not immutable.
    hostname             TEXT        NOT NULL,
    os_version            TEXT,
    cpu                   TEXT,
    logical_cores         INTEGER,
    ram_total_mb          INTEGER,
    gpu_name              TEXT,
    vram_total_mb         INTEGER,
    gpu_driver            TEXT,
    agent_version         TEXT,

    -- The node's transport credential, as a digest only. Minted and rotated
    -- on every /providers/register call; never stored in cleartext. NULL for
    -- rows that predate this column and have not re-registered since.
    node_token_hash       TEXT,

    -- Metrics: the live half, overwritten wholesale by every heartbeat.
    last_status           TEXT,
    last_detail           TEXT,
    accepts_work          BOOLEAN     NOT NULL DEFAULT FALSE,
    gpu_utilisation_pct   INTEGER,
    vram_used_mb          INTEGER,
    temperature_c         INTEGER,
    ollama_reachable      BOOLEAN     NOT NULL DEFAULT FALSE,
    ollama_version        TEXT,

    -- Models actually resident on this machine's disk (Ollama Cloud pointer
    -- entries are filtered out by the agent before sending). Bounded to 200
    -- entries of at most 200 characters each at the Pydantic layer
    -- (models.py MODEL_NAME / Metrics.local_models) — not enforced again
    -- here; see §6.6.
    local_models          TEXT[]      NOT NULL DEFAULT '{}',

    -- Whether this specific machine's owner has opted into rendering
    -- (untrusted .blend execution). Fails closed by default; only ever
    -- flipped TRUE by an operator's UPDATE, never by the agent. Reset to
    -- FALSE on every re-registration — see §5's re-registration row.
    render_eligible        BOOLEAN     NOT NULL DEFAULT FALSE,

    -- The Blender release the agent found locally, e.g. "4.3.2", or NULL.
    -- A capability report, not a permission — render_eligible is the
    -- permission.
    blender_version        TEXT,

    registered_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_heartbeat_at       TIMESTAMPTZ
);

-- Serves "most recently seen first" (list_nodes) directly.
CREATE INDEX provider_nodes_heartbeat_idx
    ON provider_nodes (last_heartbeat_at DESC NULLS LAST);
```

Deliberately **absent**, and this is load-bearing rather than an oversight:

- **No `is_online` / `status` / `liveness` column.** Liveness is derived at
  read time from `last_heartbeat_at`. See §3.
- **No credential in cleartext**, only `node_token_hash`.
- **No `provider_account_id`.** That column belongs to ADR 0005
  (`docs/yogitasks.md` Y6–Y11), added nullable when that work lands. See §6.4.
- **No `deleted_at` / soft-delete column.** There is no delete path for a
  node today (ADR 0004 point 3); a node that stops heartbeating simply reads
  `offline` forever until it heartbeats again. Adding delete semantics is out
  of scope for Y3.

## 2. Identity & persistence

**`node_id` is the primary key and there is no separate surrogate key.**
That is a deliberate choice, not the absence of one.

- `node_id` is derived, not generated, by `agent/identity.py::_derive()`: a
  SHA-256 of a namespace salt plus the Windows `MachineGuid`
  (`HKLM\SOFTWARE\Microsoft\Cryptography`), truncated to 32 hex characters. On
  a non-Windows dev machine, or when the registry key is unreadable, it falls
  back to a random UUID — which is exactly why the result is persisted rather
  than re-derived every call.
- It is written to `%LOCALAPPDATA%\GPUProvider\node_id` on first use and read
  from there on every subsequent launch (`node_id()`, read-then-write). This
  is what makes it stable **across daemon restarts**: the agent does not
  re-derive and re-send a fresh id every time it starts; it reads the one
  file that is now the authority.
- `POST /providers/register` is an **upsert keyed on this id**
  (`ON CONFLICT (node_id) DO UPDATE ...`), explicitly so that restarting the
  agent twenty times leaves one row, not twenty, and — critically —
  `registered_at` is excluded from the `SET` clause so it is never
  overwritten. That column is the only tenure signal the system has.
- The pattern is validated at the edge
  (`NODE_ID = Field(pattern=r"^[a-z0-9][a-z0-9-]{7,63}$")` in
  `orchestrator/models.py`), which both rejects malformed/injected values
  before they become a primary key and happens to satisfy Postgres `TEXT`
  with no length ceiling of its own.

**Why a natural/derived key instead of a surrogate integer + a separate
unique `node_id` column:** every other table that references a node
(`inference_requests.node_id`, `inference_jobs.node_id`) does so directly by
this value, and the value is already globally unique and stable per machine.
A surrogate key would add a join with no benefit — nothing needs to change
`node_id` in place while keeping the same row, because nothing currently
supports that operation at all (see §6.3).

**What survives a restart, and what doesn't:**

| Event | `node_id` | Row identity | Tenure (`registered_at`) |
|---|---|---|---|
| Agent process restart | same (read from disk) | same row | preserved |
| App reinstall/upgrade, same machine | same (MachineGuid unchanged) | same row | preserved |
| `%LOCALAPPDATA%` wiped, MachineGuid unchanged | same (re-derived, matches old id) | same row | preserved |
| Windows repair install that rewrites `MachineGuid` | **different** | new row; old row orphaned | lost — the machine looks new |
| Non-Windows dev environment | random per install unless the state file is preserved | new row unless disk state survives | lost |

`node_id` proves *which machine is speaking*, never *that it is really that
machine* — that is `node_token_hash`'s job, and per ADR 0004 it is
intentionally weak until `agent/core/creds.py` (hand-built, unwritten)
replaces the plaintext-file storage this currently relies on.

## 3. Liveness & staleness rules

**Liveness is derived, never stored**, and this is argued at length in
`orchestrator/liveness.py`'s own module docstring: a stored `is_online` flag
needs something that keeps it current, and when that something (a sweeper) 
dies, every row keeps whatever it last had and nothing raises. A value
computed fresh from `last_heartbeat_at` at every read cannot lie about a
heartbeat that never arrived.

**The rule, exactly as shipped** (`liveness(last_heartbeat_at, now, ttl)`):

| Condition | Result |
|---|---|
| `last_heartbeat_at IS NULL` | `never_seen` |
| `now - last_heartbeat_at <= ttl` (inclusive) | `online` |
| `now - last_heartbeat_at > ttl` | `offline` |
| `last_heartbeat_at` is in the future (clock skew) | `online` |

- **TTL**: `DEFAULT_TTL = 120s`, matching `PROVIDER_TTL_MS=120000` in
  `.env.example` — a test (`test_default_ttl_matches_the_documented_env_default`)
  exists specifically so the two cannot silently drift apart.
- **Heartbeat cadence**: the orchestrator advertises `HEARTBEAT_SEC=15` to
  every agent via `heartbeat_interval_s` in both the register and heartbeat
  responses, so the interval is server-controlled and can change fleet-wide
  without a new desktop build. 120s / 15s ≈ 8 missed heartbeats of slack
  before a node reads offline — deliberately forgiving of a brief Wi-Fi blip.
- **Who computes it**: nobody writes it. `orchestrator/liveness.py::liveness()`
  is a pure function with no I/O, called at read time by every endpoint that
  needs it (`list_nodes`, the dispatch candidate query). There is no
  worker, sweeper, or cron job, and Y3 should not introduce one — the
  repository has made this argument four times already for four different
  timers (this one, session expiry, inference-job lease reclaim, render-job
  status) and reversing it here would be the one inconsistent case.
- **`never_seen` is kept distinct from `offline` on purpose.** A node that
  registered and never heartbeated is a broken install; a node that
  heartbeated and stopped is a machine that went to sleep or lost power.
  Collapsing them loses the one signal that tells a dead agent from a dead
  machine.
- **Future timestamps are treated as online**, accepting consumer-desktop
  clock skew as normal. The code is explicit that this is safe only because
  nothing is metered from a heartbeat timestamp yet — the moment a timestamp
  affects payment or a lease, skew becomes something an attacker can use and
  this rule needs revisiting.

**"Stale" does not exist as a state in the shipped code**, and that is worth
naming plainly rather than glossing over, because Y3's own checklist asks for
an `online → stale → offline` transition table. What exists is binary
(`online` / `offline`, plus `never_seen`). `docs/Tasks/tasks.md`'s M1 tracker
and `README.md` both use the phrase "stale → offline (TTL)" to describe the
*same* transition this document calls `online → offline` — "stale" there is
prose for "past its TTL," not a third classification. See §6.2 for the open
question this creates.

## 4. Index strategy

**Shipped today:**

```sql
CREATE INDEX provider_nodes_heartbeat_idx
    ON provider_nodes (last_heartbeat_at DESC NULLS LAST);
```

This serves `GET /providers/nodes`
(`ORDER BY last_heartbeat_at DESC NULLS LAST, registered_at DESC`) directly —
the fleet console page, which is read far more often than the table is
written to, and is always ordered by recency of contact.

**Write path**: every heartbeat is a single-row `UPDATE ... WHERE node_id =
%s`, served by the primary key. Heartbeats are frequent (every 15s per
active node) and the index above has one column, so its maintenance cost per
write is one B-tree entry move — cheap at any fleet size this product is
likely to reach before Y4 revisits it.

**Dispatch/matching query, as it exists today**
(`orchestrator/main.py` ~line 1629):

```sql
SELECT node_id, hostname, accepts_work, ollama_reachable,
       local_models, registered_at, last_heartbeat_at
FROM provider_nodes
WHERE accepts_work = TRUE
  AND ollama_reachable = TRUE
  AND last_heartbeat_at IS NOT NULL
ORDER BY last_heartbeat_at DESC
```

Model-name matching (`local_models`) is **not** done in SQL — the query
above fetches every currently-eligible node and `local_models` membership is
checked in Python afterward
(`if model in (row["local_models"] or [])`, main.py:1662). At current fleet
sizes that is the right call; it is worth naming as a scaling boundary
rather than an oversight, because it is exactly the kind of thing that stops
being fine silently.

**Recommended for Y4, not proposed as new work now:**

- A **partial index** matching the dispatch predicate exactly —
  `ON provider_nodes (last_heartbeat_at DESC) WHERE accepts_work AND
  ollama_reachable` — once the unfiltered `provider_nodes_heartbeat_idx`
  scan of all rows (idle and active) becomes measurably more expensive than
  a scan restricted to the eligible subset. Not worth adding pre-emptively
  at fleet sizes where "every row" and "every eligible row" are close to the
  same number.
- A **GIN index on `local_models`** (`local_models @> ARRAY[...]` /
  `... = ANY(local_models)`), to move model-membership filtering into SQL —
  worth adding in the same change that writes the SQL query using it, the
  same way `inference_jobs_claimable_idx` and `render_frames_claimable_idx`
  were each added alongside the query they serve, not ahead of it.
- **Hardware-matching indexes** (`gpu_name`, `vram_total_mb`) for the
  GPU-model/VRAM discovery queries this task's checklist names. No such
  query exists in the live code yet — the only matching filter today is
  liveness plus `accepts_work`/`ollama_reachable`. `docs/ROLES.md`'s
  "weighted recency scoring" / `matching.ts` material describes the frozen
  TypeScript gaming backend, not this table. These indexes should land with
  the M2 capacity-matching query that actually needs them, not before —
  matching the convention every other index in `schema.sql` already follows
  (each one is commented with the exact query it exists for).

`node_token_hash` needs no index: it is looked up only by `node_id`, already
the primary key (`_authenticate_node` selects the row by `node_id`, then
compares hashes in application code).

## 5. Lifecycle state machine

| From | To | Trigger | Actor | Where |
|---|---|---|---|---|
| *(no row)* | `never_seen` | `POST /providers/register` inserts the row; `last_heartbeat_at` starts `NULL` | Agent | `orchestrator/main.py::register` |
| `never_seen` | `online` | First successful `POST /providers/heartbeat` sets `last_heartbeat_at = now()` | Agent (write); derived at next read | `orchestrator/main.py::heartbeat`, `liveness.py` |
| `online` | `online` | Any heartbeat arriving within TTL of the previous one | Agent | `heartbeat` |
| `online` | `offline` | **No write occurs.** The next read of the row happens more than TTL after the stored `last_heartbeat_at` | *(nobody — purely derived)* | `liveness.py`, evaluated by every caller of `list_nodes` / the dispatch query |
| `offline` | `online` | Any subsequent successful heartbeat | Agent | `heartbeat` |
| any state | *(hardware facts refreshed, credential rotated, `render_eligible` reset to `FALSE`)* | `POST /providers/register` again (app restart) | Agent | `register` — does **not** touch `last_heartbeat_at`, so it has no effect on liveness classification |
| any state | *(terminal, not modeled)* | Node is uninstalled or permanently retired | — | **No delete endpoint exists.** The row stays `offline` forever, unless a heartbeat arrives again. Deregistration is explicitly out of scope per ADR 0004 point 3. |

Two things about this table are easy to misread and are worth stating
directly:

- The `online → offline` edge has **no actor and no write**. It is not a
  transition the system performs; it is a fact that becomes true about a row
  that nothing has touched, the instant more than `ttl` elapses. This is the
  entire point of §3 — there is nothing to trigger, so there is nothing that
  can fail to trigger.
- Re-registration is not a liveness event. An agent that restarts mid-session
  re-upserts its hardware row and gets a new credential, but a node that was
  `online` a second before its restart is still `online` a second after,
  because `register` never writes `last_heartbeat_at`.

**`stale` is absent from this table for the reason given in §3**: it is not
implemented. If R1 confirms a real three-state model is wanted (see §6.2),
this section is where its trigger and actor would be added.

## 6. Open questions & alignment (for R1)

1. **`packages/contracts/` does not describe this table, and this task's own
   instruction to treat it as the authoritative contract appears stale.**
   `packages/contracts/src/schemas.ts` defines `ProviderHeartbeatSchema`,
   `ProviderCapabilitySchema`, `ProviderMetricsSchema`, and match/job request
   schemas for a different product surface entirely — camelCase fields
   (`providerId`, `gpuVramGb`, `supportsGaming`, `region`, `avgRttMs`), a
   gaming/compute-match shape, no `node_id` pattern, no heartbeat TTL, no
   liveness concept. None of it lines up with `orchestrator/models.py`'s
   `Capability` / `Metrics` / `HeartbeatRequest`, which is the actual, live,
   enforced wire contract for this table. Per ADR 0002/0003, `packages/
   contracts` is frozen reference from the pre-pivot gaming design and this
   is a concrete instance of that staleness showing up where a task
   description assumed otherwise. **Ask for R1**: should `packages/
   contracts` be explicitly marked non-authoritative for anything
   inference-beachhead-related (a note at the top of the file would do it),
   updated to actually describe `Capability`/`Metrics`/`NodeView` for a
   future TypeScript consumer, or left alone with this document standing as
   the correction? This document treats `orchestrator/models.py` as ground
   truth, not `packages/contracts`.

2. **Does `stale` need to become a real third state, or is the task's
   wording just describing the existing `online → offline` edge?** Nothing
   in the shipped code has three liveness states — see §3. If a genuine
   intermediate state is wanted (e.g., "missed one heartbeat, deprioritize
   in matching, but don't drop from the console yet" — the kind of thing
   `docs/PLAN.md` §7's "weighted recency scoring" gestures at), it should
   stay **derived**, the same way `online`/`offline` already are, via a
   second threshold in `liveness.py` (e.g. `stale` between `0.5×ttl` and
   `ttl`) rather than a stored column — reversing the derived-not-stored
   argument for this one state and not the others would be inconsistent
   with every other staleness decision in this codebase. **Ask for R1**:
   confirm whether M1's Pydantic models (`NodeView.liveness`) should grow a
   third literal value, and if so, at what threshold and for what
   consumer (UI badge? matching deprioritization? both?).

3. **`node_id` has no rotation or supersession path.** Per §2, a Windows
   repair install (or any MachineGuid change) silently orphans the old row
   and creates a new one with no link between them — the provider loses
   their tenure record with no error and no recovery. Out of scope for M1
   per ADR 0004, but Y4 is about to write a migration, which is the moment
   to decide rather than to let the shape freeze further. **Ask for R1**:
   is a `superseded_by node_id` (self-referencing, nullable) column worth
   adding now, or does this wait for provider accounts (ADR 0005), where
   identity could instead be re-anchored to `provider_account_id` and this
   problem mostly disappears?

4. **`provider_account_id` is deliberately not in this document's DDL.**
   ADR 0005 assigns that column to Y6–Y11 as nullable, added when that work
   lands, mirroring how `marketplace_api_keys.user_id` arrived. **Ask for
   R1**: confirm Y4's migration should not pre-allocate a slot or placeholder
   for it — one additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` when
   ADR 0005 actually ships is simpler than reasoning about an empty column
   sitting unused in the meantime.

5. **Discovery-by-hardware indexes are named in the Y3 checklist but nothing
   in the live code queries on them yet.** See §4. **Ask for R1**: confirm
   the plan is to land `gpu_name`/`vram_total_mb`/`local_models` indexes in
   the same change as the M2 matching query that filters on them, not ahead
   of it — consistent with how every existing index in `schema.sql` is
   commented with the specific query it serves.

6. **`accepts_work` and `ollama_reachable` are independently agent-reported
   and nothing prevents an inconsistent combination** (`accepts_work=TRUE`,
   `ollama_reachable=FALSE`) from being stored — the dispatch query's
   `AND ollama_reachable = TRUE` guard means it is filtered at read time, but
   the row itself can still say something incoherent. **Ask for R1**: is
   that read-time guard considered sufficient, permanently, or should
   `HeartbeatRequest` (M1 Pydantic, R1-owned) reject `accepts_work=True`
   combined with `ollama_reachable=False` at the edge instead of storing it
   and filtering it out downstream?

7. **`node_id`'s format constraint lives only in Pydantic, not in the
   database.** `NODE_ID`'s pattern (`^[a-z0-9][a-z0-9-]{7,63}$`) is described
   in `models.py` as "load-bearing, not decoration," but `schema.sql` has no
   matching `CHECK` constraint — the database trusts the application layer
   alone. **Ask for R1**: is a `CHECK (node_id ~ '^[a-z0-9][a-z0-9-]{7,63}$')`
   worth adding for defense in depth, or does duplicating the pattern in two
   places create its own drift risk (one gets updated, the other doesn't)
   that outweighs the benefit?
