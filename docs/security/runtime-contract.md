# Provider runtime security contract

This document defines the platform-neutral boundary implemented by
`security/runtime_contract.py`. It is intended for the Windows and Linux runtime
owners to integrate without moving sandbox logic into the orchestrator.

## Inputs

### Node security posture

- service-generated opaque `node_alias`, never a hostname or hardware ID;
- tier and eligible workload classes;
- sandbox kind/version;
- signed agent digest and allowlisted worker-image digests;
- disk-encryption, dedicated-GPU, and attestation state;
- timezone-aware last successful security-audit timestamp.

Posture is security evidence, not a provider assertion. The production source
must be signed attestation plus server-side enrollment state. The current
provider heartbeat alone does not meet this requirement.

### Sandbox policy

- opaque job alias and workload class;
- exact immutable image digest;
- one or more centrally allowlisted signed agent digests;
- positive wall deadline, CPU, RAM, scratch, and non-negative VRAM limits;
- explicit outbound hostname allowlist, empty by default.

The job envelope must contain only the minimum workload input. It must not carry
customer account identity, customer/provider IP, original filename/path,
long-lived credential, general bucket credential, or unrelated session history.

## Admission

Unknown values fail closed. The evaluator checks tier, workload eligibility,
allowlisted image, audit freshness, attestation and encrypted disk. Render and
cloud gaming additionally require an approved full-VM kind and dedicated GPU.
Stable reason codes are returned for bounded-cardinality metrics.

`SecurityController.begin()` permits only one active job. A quarantined or busy
node cannot claim. Admission state must be stored durably by a platform runner;
the in-memory class is a reference state machine, not production persistence.

## Terminal cleanup sequence

1. Stop lease renewal and prevent any new claim.
2. Kill the complete workload/VM process tree from outside the guest.
3. Destroy the per-job data-encryption key.
4. Destroy the encrypted ephemeral volume and all runtime temp paths.
5. Detach, reset and verify/scrub the dedicated GPU.
6. Remove job network policy and transfer capability.
7. Reconcile orphan runtime objects and scan for synthetic markers.
8. Produce and sign the cleanup receipt.
9. Centrally verify it; only a fully successful receipt clears the active job.

Missing evidence, invalid signature, time inversion, non-zero marker recovery,
job mismatch, verifier exception, or any false cleanup check quarantines the
node. A restart with an active/orphan object does the same. There is deliberately
no automatic method to clear quarantine; operator recovery requires a fresh
audited workflow and credential rotation when indicated.

## Signature profile

The canonical payload is sorted, compact UTF-8 JSON with UTC ISO-8601 times.
Production signs those exact bytes using an attested, hardware-backed asymmetric
key. Verifiers bind `signer_key_id` to the enrolled node, validate the chain,
algorithm, revocation, key usage, node state, and replay protection. A TPM-backed
key can show possession, but a compromised host may still invoke it; receipt
signatures are not a replacement for measurement attestation.

HMAC is acceptable only in unit tests. A provider-readable shared secret is not
valid production cleanup proof.

## Event profile

Emit only these lifecycle facts: event schema version, UTC timestamp, opaque
node/job/sandbox aliases, workload, image digest, outcome, bounded reason code,
duration bucket, and trace ID generated by the platform. Never emit prompt,
response, source/artifact name, path, URL/query string, token, customer ID,
provider hardware ID, IP, exception body from customer input, or raw policy.

Metrics labels are limited to workload, tier, sandbox kind, image release,
outcome, and bounded reason. Node/job/sandbox/trace identifiers are log fields,
never metric labels.

## Integration acceptance tests

- normal completion, cancellation and timeout;
- guest crash, Blender crash and complete process-tree termination;
- supervisor crash before and during every cleanup step;
- host sleep/resume, reboot and simulated sudden power loss;
- missing/tampered/replayed/mismatched receipt;
- key/volume/temp/network/GPU cleanup failure independently;
- marker recovery from the next job and startup orphan discovery;
- denied Internet, DNS, LAN, host, metadata, SMTP and SMB access;
- log/trace/metric scanning with seeded tokens, URLs, paths and prompts;
- simultaneous claim attempts and lease expiry during cleanup.

The required invariant is: cleanup receipts cover 100% of terminal customer
jobs, zero canaries are recovered, and no later tenant starts after an unverified
cleanup.
